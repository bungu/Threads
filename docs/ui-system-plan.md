# Threads UI付きシステム 実装計画

更新日: 2026-10-05
状態: 要件確認済み・実装開始前

## 1. 確定した要件

- 現在のインラインHTMLを画面の原本として、そのHTML/CSSを直接利用する。追加機能の領域を除き、見た目を完全に一致させる（ユーザー明示要件）。
- 利用者は本人のみ。初期運用はThreads 1〜5アカウント。
- Google Cloud上で稼働し、ブラウザやMacを閉じていても定期投稿する。
- Threads公式APIを使う。最初はアカウントごとのユーザーIDとアクセストークンを手動登録する。
- Meta開発者アプリは作成済み。利用者側で実投稿を確認済みのアカウントがある。
- アカウントごとにプロンプト・曜日・時刻・定期投稿ON/OFFを保存する。
- 指定時刻にGeminiで生成し、そのまま自動投稿する。承認操作は挟まない。
- 本文は140文字以内。現在のPro→Flashフォールバックを引き継ぐ。
- 時刻の表示と曜日判定は日本時間。内部の実行時刻はUTCでも保存する。
- アカウント一覧画面は設けない。左側からアカウントを直接切り替える。
- アカウント数の数字、削除済みの説明文・コピーは再追加しない。アイコンは無地。
- プロンプト見出しは「プロンプト」、保存ボタンは「変更を保存」。初期状態の保存案内文は表示しない。

「そのまま利用」は、原本のHTML/CSSと画面構成を製品画面に移し、追加機能以外は見た目を完全に一致させることを意味する。実データ接続のため、JavaScriptの保存・読み込み処理、デモデータ、ホスト依存部分を置き換える。画面を別フレームワークで再制作する工程は設けない。

### 見た目の一致を保証する実装・検証方針

- 既存領域の配置、寸法、余白、フォント、文字サイズ、行間、文字の太さ、色、枠線、角丸、影、アイコン、文言、改行、レスポンシブ切り替え条件を固定する。
- 新しいCSSリセットやUIライブラリの既定スタイルが既存領域へ作用しない構成にする。会話ランタイム由来のフォント・テーマ・アイコンの表示条件も原本と揃える。
- 本番データに伴うアカウント名・プロンプト・本文・日時・状態の変化と、デザイン変更を区別する。比較には両方で同じ固定データと時刻を使う。
- 追加機能は必要時に開く接続設定・ログイン・エラー詳細などに限定し、通常時の既存画面を押し広げたり、再配置したりしない。
- 原本と製品画面を、同じブラウザ・表示倍率・端末倍率・フォント・テーマ・画面幅・操作状態で撮影し、画像を重ねて比較する。
- 比較対象は初期画面、アカウント切り替え、未保存、保存後、ON/OFF、時刻追加、モバイル表示。明暗テーマも原本が対応する範囲で比較する。
- **受入条件は「追加機能の領域を除いた既存UIの視覚差分ゼロ」**。追加領域の除外で既存領域の位置ずれを隠さない。差分が出た場合は原因を直してから完了とする。
- ブラウザやOSが異なる場合の文字描画差を避けるため、同一環境での原本比較を判定基準にする。

## 3. 採用する構成

| 役割 | 構成 |
| --- | --- |
| UI・設定API | Python / FastAPI + 現在のHTML、Cloud RunのWebサービス |
| 定期投稿 | Cloud Runの認証必須ワーカーサービス。既存Python処理を利用 |
| 時刻起動 | Cloud Schedulerが5分ごとにワーカーを呼び出す |
| 設定・実行履歴 | Firestore。アカウント別設定・実行枠・結果・処理権を永続化 |
| 秘密情報 | Secret Manager。Geminiキーとアカウント別Threadsトークンを保存 |
| 管理画面ログイン | ローカルは `setting.py`、クラウドは同じ文字列を Secret Manager から読み、署名付きセッションCookieを発行 |
| ログ | Cloud Logging。本文やトークンを通常ログに出さず、実行ID・状態・失敗分類を記録 |

Webとワーカーは同じコード・コンテナを使い、起動対象と権限を分ける。Schedulerからワーカーへは専用サービスアカウントの認証を使う。クラウド内で待機するPythonタイマーや、ブラウザ内タイマーには依存しない。

Cloud Schedulerから認証付きCloud Runを起動する構成は公式の対応範囲。[Google公式手順](https://docs.cloud.google.com/run/docs/triggering/using-scheduler)

Cloud Runの一時ファイル領域はインスタンス停止で失われ、インスタンス間で共有されないため、本番のSQLite置き場にはしない。[Google公式説明](https://docs.cloud.google.com/run/docs/configuring/services/ephemeral-disk)

## 4. HTMLを実システムにつなぐ作業

1. 原本をプロジェクト内のUIディレクトリへコピーし、比較用の原本も保管する。
2. スタンドアロンHTMLの外枠を加える。フォント・アイコン・テーマ設定を明示し、会話側のランタイムに依存せず同じ表示にする。
3. `window.openai.widgetState` / `setWidgetState` をサーバーへの読み書きへ置き換える。デザイン調整用のTweak連携は製品側から外す。
4. 固定のサンプルアカウントを削除し、APIから取得した実アカウントを表示する。未登録時には既存の「アカウントを追加」へ誘導する空状態を表示する。
5. ボタン・入力欄・切り替え操作の位置と見た目は原本を維持する。
6. 右側の「NEXT POST」はサーバーの保存済み設定から算出した予定を表示する。未保存の変更は実投稿予定に反映しない。
7. 「投稿イメージ」の固定サンプル本文を、そのアカウントで最後に実際に生成した本文へ置き換える。未生成時は空状態にし、サンプル用のタグを実行状態に置き換える。
8. 追加する画面は、ログイン・アカウント接続情報・エラー詳細など、その操作時だけ開く小さな画面に限る。

### 保存の動作

- 「変更を保存」は選択中のアカウントだけを保存する。
- 曜日・時刻・プロンプト・ON/OFFをまとめて検証し、成功時のみ反映する。
- 保存失敗時は入力内容を保持する。保存中は二重送信を防ぐ。
- 切り替え時はアカウント別に未保存の入力を保持し、再読み込み・画面離脱時には未保存を知らせる。
- 同じ画面を複数タブで編集した場合は、設定の版番号で上書き競合を検出する。
- 既存のプロンプト上限2,400文字、最大6時刻/日の操作を引き継ぐ。本文の140文字上限とは区別する。

## 5. アカウント登録と認証情報

- 「アカウントを追加」からユーザーID・アクセストークンを登録し、Threads APIで本人のアカウント情報と接続を確認する。
- ユーザーIDとトークンの対象が一致することを確かめ、表示名・ユーザーネームを取得する。画像は取得しても表示に使わず、無地アイコンを維持する。
- 投稿権限を検証し、足りない場合は定期投稿ONで保存できないようにする。登録時に勝手に投稿しない。
- 新規登録時は定期投稿OFF。プロンプトとスケジュールを保存してからONにする。
- トークンの実体はSecret Managerへ保存し、Firestoreには参照・期限・接続状態だけを置く。読み取りAPIからトークンを返さない。
- トークンを更新できる接続設定を、アカウント見出し付近の小さな操作から開く。接続解除も同じ画面にまとめる。
- 接続解除は先に定期投稿を停止し、保存済み予約を無効化する。実行履歴は残す。
- 長期トークンを前提に、期限情報を記録して失効前の更新処理を実装する。短期トークンの場合は長期化の準備を案内する。長期化に必要なアプリシークレットは管理者用の初期設定で扱う。
- 更新や接続検証に失敗した場合は対象アカウントを停止し、画面に再接続の操作を表示する。

公式APIには長期トークンへの交換と期限内の更新手段がある。[Meta公式Authorization](https://www.postman.com/meta/threads/folder/34203612-e0373e84-de6b-46f1-b90d-3fea76ba6782)

秘密情報はサーバー側だけで読み出す。管理画面は `setting.py` のログイン文字列の照合、HttpOnly/Secureの署名付きセッション、CSRF対策を実装する。Firestoreをブラウザから直接操作させない。[Secret Manager](https://docs.cloud.google.com/secret-manager/docs/overview)

## 6. 定期投稿の仕様

### 通常の実行

1. Schedulerが5分ごとに起動する。
2. 保存済み設定から実行予定を検索する。
3. `アカウントID + 予定日時` を一意な実行枠として、Firestoreのトランザクションで確保する。
4. 使用した設定の版番号とプロンプトを実行記録へ保存する。
5. Geminiで本文を生成し、140文字以内・空でないことを確認する。
6. 保存済みON/OFF・設定の版番号・処理権を再確認する。
7. Threadsのコンテナを作成し、準備完了後に公開する。
8. 本文・投稿ID・結果・次回予定を保存して画面へ反映する。

1〜5アカウントの同時刻投稿を処理できるよう、アカウント単位で独立して実行する。同じアカウントでは複数の投稿処理を同時に進めない。ワーカーはHTTPリクエスト内で完了を待ち、返答後のバックグラウンド処理に依存しない。

### 時刻と停止

- 設定時刻は「生成・投稿処理を始める時刻」。実際の公開には起動間隔と生成/API処理時間が加わる。秒単位の定刻公開は保証しない。
- 定期投稿OFFの保存が成功した後は、新しい公開要求を開始しない。すでに公開要求を送信済みの投稿は取り消せないため、結果を記録する。
- 生成中にプロンプトや予定が保存し直された場合は、古い版の未公開ジョブを中止し、新しい将来予定に反映する。同じ実行枠を自動で作り直して再投稿しない。
- 障害からの復帰時は、未処理で5分以内の予定のみ遅延実行する。古い予定はスキップとして記録し、一度に過去分を投稿しない。この5分は初期運用の提案値。

### 二重投稿と失敗

- Schedulerの再配信や同時実行を想定し、実行枠の一意性と処理権をDBで管理する。プロセス内ロックだけでは防がない。
- 一定時間で失効する処理権と所有者IDを使い、古いワーカーが公開に進まないよう検証する。
- 公開要求前に状態を永続化する。公開要求後に通信が切れた場合は「結果不明」とし、自動再送しない。
- 結果不明のアカウントだけを止め、他のアカウントは継続する。UIから実行詳細と復旧操作を開けるようにする。
- 生成失敗・認証切れ・明確なAPI拒否・公開結果不明を区別する。再試行は公開前に安全と確認できる工程に限定し、回数を制限する。
- 認証切れは再接続へ、結果不明はThreads上の照合と確定操作へ誘導する。エラーを保存成功表示に置き換えない。

Cloud Schedulerは同じ実行を複数回配信し得るため、呼び出される側で重複に耐える設計が必要。[Google公式の配信仕様](https://docs.cloud.google.com/scheduler/docs/overview)

## 7. 保存データとAPIの範囲

### Firestore

- accounts: 所有者、ThreadsユーザーID、表示名、ユーザーネーム、接続状態、トークン参照・期限。
- settings: アカウント別プロンプト、曜日、時刻、ON/OFF、タイムゾーン、版番号、更新日時。
- runs: 実行枠ID、アカウントID、予定時刻、プロンプトと設定版の記録、本文、処理状態、コンテナID、投稿ID、エラー分類、処理権。
- runtime: 全体の定期実行有効化状態、最終定期起動時刻。テストと初回リリースでは全体停止を既定にする。

### API

- ログイン・ログアウト・現在のユーザー。
- アカウント一覧取得（サイドバー用）、接続確認、追加、トークン更新、接続解除。
- アカウント別設定の取得・検証・保存。
- 次回予定と直近実行結果の取得、結果不明の照合後の確定。
- ワーカー専用の定期処理。ブラウザ用APIと認証を分離する。

トークンを含む入力はログ・URL・ブラウザの保存領域に残さない。認証エラーの元レスポンスをそのまま画面へ返さない。

## 8. 実装順序と完了条件

| 段階 | 作業 | 完了条件 |
| --- | --- | --- |
| 1. 土台の整合 | 140文字にテスト・READMEを統一。HTML原本と比較画像の保管、独立表示 | 既存テスト全件成功。固定データによる原本との視覚差分ゼロ |
| 2. UIと保存 | FastAPI、アカウント別設定、Firestore、保存・再読み込み・入力検証 | 再起動しても設定が残り、アカウント間で内容が混ざらない |
| 3. 接続とログイン | 本人限定ログイン、手動登録、接続検証、秘密保存、期限管理 | 第三者は設定にアクセスできず、登録・更新・再接続できる |
| 4. 自動投稿 | Scheduler、実行枠、処理権、Gemini/Threads連携、失敗時の停止・復旧 | 二重起動で二重投稿しない。停止・設定更新が正しく反映される |
| 5. 画面結合 | 次回予定・最後の生成本文・接続不備・実行結果を画面へ表示 | ダミーデータがなく、保存結果・実行結果が画面と一致する |
| 6. 検証と公開準備 | ブラウザ確認、クラウド設定、ログ、費用見積もり、ロールバック手順 | 追加機能以外の視覚差分ゼロ、主要操作、障害系、認証の確認が完了 |
| 7. 実機確認と稼働 | 既存アカウントを接続して生成を確認し、指定の1投稿を照合後、定期実行を有効化 | ブラウザを閉じても予約投稿でき、停止と結果確認ができる |

今回は計画作成のみ。クラウド環境の作成、認証情報の登録、実投稿、定期実行の有効化はまだ行わない。

## 9. 検証対象

- 140文字の境界、Pro失敗時のFlash切替、生成失敗時の投稿抑止。
- アカウント間の設定・トークン・履歴の分離、ユーザーID不一致、トークン更新失敗。
- JSTの曜日、日付境界、重複時刻、ON/OFF、再起動、遅延実行とスキップ。
- 同じ実行枠の同時確保、タイムアウト、途中終了、公開結果不明、復旧時の再送抑止。
- 未認証・別ユーザー・CSRF・設定の版競合・API入力不備。
- 元HTMLと本番表示を同一環境・データ・時刻・状態で画像比較。幅1,024px / 736px / 320pxで、追加機能以外の視覚差分ゼロを確認する。
- 最後に実APIで生成と指定のテスト投稿を確認する。自動テストは実投稿しない。

## 10. 実装開始後の初期設定で必要な情報

以下は計画を妨げない。接続・デプロイの段階で確認する。

- 使用するGoogle CloudプロジェクトID。専用プロジェクトを基本案にし、既存を使う場合はサービス・データ・権限を分ける。
- 管理画面用の推測されにくいログイン文字列。
- Geminiの利用可能なAPIキーと、現在のモデル設定が利用できること。
- 各ThreadsアカウントのユーザーID、長期アクセストークン、対象アプリの情報。秘密情報はチャットではなく、初期設定・接続画面から入力する。
- 最初の実投稿確認に使うアカウント・本文・時刻。
- クラウド利用の月額上限。リソース作成前に想定アカウント数・投稿回数に基づく見積もりを提示する。予算通知だけでは課金停止にならないため、最大インスタンス数や実行回数の上限も設ける。

初期版はCloud Runの標準URLを利用する。独自ドメイン、共同管理、画像投稿、分析画面は別要件が出た時点で追加を検討する。
